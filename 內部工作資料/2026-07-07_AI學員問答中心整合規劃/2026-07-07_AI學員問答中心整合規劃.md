  - 若 LLM 出錯或不安全，自動 fallback 到規則引擎。

  - 測無 key fallback。
  - 測 unsafe LLM fallback。
  - 測 safe LLM used。
  - 測認同閘門仍由規則引擎控制。

### OpenAI 安全架構

```text
request
  -> state-machine deterministic result
  -> retrieve knowledge by phase
  -> build prompt
  -> OpenAI Responses API
  -> parse JSON reply
  -> safety-check
  -> safe: replace reply only
  -> unsafe/error: fallback deterministic result
```

2. 用幾個一問一答找出他的銷售天賦與行為模式。
3. 產出一份「你的銷售天賦規格」。
4. 問：「你覺得有準嗎？像你嗎？」
5. 如果使用者回答像、準、有中、滿符合，才自然銜接：
   - 「那如果持續去學習這幾個課程順序的話，你的未來會進步得更快。」
6. 再給課程順序、原因與 CTA。

避免事項：

- 不要一開始就推課程。
- 不要把診斷結果直接包成銷售話術。
- 不要在使用者還沒認同之前，就要求報名或點 LINE。
- 不要讓 AI 表現得像客服機器人，要像泰欣老師在陪他釐清自己。

### 後台判斷流程

後台不要全部交給 LLM 自由判斷。建議用「規則引擎 + RAG 檢索 + LLM 生成」三層：

```text
前端送出資料 / 訊息
  -> API preflight
  -> Session state 讀取
  -> 規則引擎計算可驗證資料
  -> 對話證據抽取
  -> DISC / 銷售天賦 / 卡點分數更新
  -> 判斷目前階段
  -> 決定下一步：追問 / 出規格 / 等認同 / 推課 / 真人接手
  -> RAG 取用對應知識
  -> LLM 產生泰欣老師口吻回答
  -> 後處理安全檢查
  -> 回傳前端
```

#### 1. API preflight

每次呼叫 `/api/student-qa/chat` 先做：

- 檢查 CORS，只允許官網網域。
- 檢查 rate limit，避免濫用。
- 檢查 request schema。
- 移除 HTML / script injection。
- 檢查是否有必要欄位：
  - session_id
  - current_phase
  - messages
  - profile
- 若有生日，先確認是西元年月日且日期合法。
- 若使用者問開課時間 / 價格，標記 `needs_offering_lookup = true`。

#### 2. Session state

後端要保存或由前端回傳 session state，至少包含：

```json
{
  "session_id": "uuid",
  "phase": "intake",
  "profile": {
    "name": "",
    "birthdate": "1990-01-01",
    "region": "tw",
    "role": "sales_consultant",
    "industry": "",
    "goals": [],
    "problems": []
  },
  "computed": {
    "life_number": null,

  },
  "scores": {

  },
  "recognition": {
    "profile_spec_shown": false,
    "user_agreed": false,
    "user_disagreed": false
  },
```

#### 3. 規則引擎計算可驗證資料

- 生涯運數：用本機生涯運數計算器邏輯計算。
- 天賦數：用生日計算。
- 地區：台灣 / 馬來西亞 / 其他。
- 課程開課時間：只讀 `course_offerings`。
- 課程金額：只讀 `course_offerings`。
- 課程連結：只讀白名單連結。
- 報名表單 / LINE：只讀設定檔。

如果 `course_offerings` 沒有資料，後端回傳：

```json
{
  "offering_status": "unconfirmed",
  "safe_reply": "我目前沒有已確認的最新開課時間與金額，不直接猜。"
}
```

#### 4. 對話證據抽取

每輪使用者回答後，後端先萃取結構化證據，再交給 LLM。

範例：

```json
{
  "evidence": {
    "disc_signals": ["I", "S"],
    "goal_signals": ["提升成交", "建立信任"],
    "problem_signals": ["客戶說再想想", "不敢逼單"],
    "emotion_signals": ["怕被拒絕", "想被客戶喜歡"],
    "objection_signals": [],
    "sales_stage_signals": ["信任建立", "成交推進"]
  }
}
```

DISC 訊號建議：

- D：講求效率、結果、直接、討厭拖泥帶水、想快速成交。
- I：重視感覺、關係、被喜歡、互動氣氛、故事與共鳴。
- S：重視安全感、穩定、不想冒犯客戶、不敢推太快。
- C：重視邏輯、資料、專業、證據、流程與標準。

#### DISC 回覆策略

後台判斷 DISC 後，不只是標註類型，還要改變 AI 的回覆方式。4U 內部站已有 DISC 變體，可作為語氣與追問策略來源，但公開回答時必須移除未確認成效數字。

| DISC | 他想聽什麼 | AI 回覆方式 | 避免 |
|---|---|---|---|
| D 型 | 結果、效率、重點、下一步 | 直接講結論，給明確路徑，少鋪陳，讓他覺得有掌控感 | 太多情緒安撫、繞圈、長篇故事、不明確 |
| I 型 | 被理解、共鳴、畫面感、正向可能 | 先接住感受，用故事和畫面描述他的優勢，讓他感覺被看見 | 太冷、太理性、只給表格、直接糾正 |
| S 型 | 安全感、穩定、不要被逼、可慢慢來 | 語氣溫和，降低壓力，給小步驟，強調可以先確認再決定 | 催促、壓迫、太強勢、逼他立刻選 |
| C 型 | 邏輯、依據、結構、可驗證資訊 | 用條列、架構、因果、判斷依據說明，讓他知道不是亂猜 | 只講感覺、誇張形容、沒有證據、跳太快 |

#### DISC 分型回覆模板

D 型：

```text
我直接講結論：你現在最大的優勢是___，最大的卡點是___。
如果這個判斷對，你接下來不用學一堆東西，先補___，最快會看到行動上的改變。
```

I 型：

```text
我覺得你很像那種靠感覺、互動和信任在成交的人。
你不是不會成交，而是當客戶的熱度掉下來時，你容易開始懷疑是不是自己不夠好。
這一點如果調整起來，你的影響力會很快被看見。
```

S 型：

```text
我先跟你說，這不是你的問題。
你比較像是需要安全感和節奏的人，所以當客戶還沒完全信任你時，你不太想推太快。
這種人其實很適合做長期關係，只是需要一套不會讓你有壓力的成交步驟。
```

C 型：

```text
我用結構幫你整理。
目前我看到三個訊號：第一，___；第二，___；第三，___。
所以我初步判斷你偏___型。這代表你在銷售上適合用邏輯、證據與流程建立信任。
```

#### DISC 追問策略

當信心不足時，用行為題追問，不直接問「你是哪一型」。

- D / I 分不清：問「你成交時更在意快速推進結果，還是更在意互動氣氛和對方喜不喜歡你？」
- I / S 分不清：問「客戶冷掉時，你比較會主動熱絡氣氛，還是會先退一步、怕造成壓力？」
- S / C 分不清：問「你不敢推進時，是因為怕對方不舒服，還是因為你覺得資料還不夠完整？」
- D / C 分不清：問「你想要快，是因為你重視結果，還是因為你已經有一套判斷標準？」

#### DISC 在不同階段的用途

- `discovery`：決定下一題怎麼問。
- `profile_spec`：決定銷售天賦規格怎麼寫。
- `accuracy_check`：決定「你覺得像嗎」的問法。
- `recommendation`：決定課程順序與說服角度。
- `objection_handling`：決定異議處理語氣。

#### DISC 對課程推薦的影響

課程推薦仍以卡點為主，DISC 只調整順序和說法，不能只因 DISC 直接推課。

- D 型：強調最快補哪個能力、下一步做什麼、不要讓他覺得流程拖。
- I 型：強調他的人際影響力、故事力、信任感如何放大。
- S 型：強調穩定步驟、安全推進、不需要逼自己變強勢。
- C 型：強調架構、標準、判斷依據、可複製流程。

#### DISC 混合型處理

若判斷為混合型，例如 `I 偏 S`：

- 主要型決定語氣。
- 次要型決定追問和風險提醒。
- 回覆格式：`你比較像 I 偏 S：外在重視互動和關係，但真正做決定時需要安全感。`
- 不用硬判單一型，混合型反而會讓使用者覺得更準。

銷售天賦維度建議：

- `lead_generation`：開發名單 / 流量。
- `trust_building`：信任建立。
- `needs_diagnosis`：需求提問與五連問。
- `value_presentation`：產品介紹 / MBAF / 言之有物。
- `objection_handling`：異議處理。
- `closing`：成交推進。
- `follow_up_system`：追蹤與系統。
- `stage_expression`：舞台表達 / 帶人說服。

#### 5. 分數更新與信心門檻

每輪回答後更新分數：

```text
DISC 分數 = 基本資料訊號 + 對話詞彙訊號 + 行為反應訊號 + 4U 對應問題樹訊號
銷售天賦分數 = 自然優勢訊號 + 成功經驗訊號 + 使用者喜歡做的銷售動作
卡點分數 = 問題複選 + 對話痛點 + 異議詞彙 + 情緒詞彙
```

信心門檻：

- `>= 0.70`：可以輸出初判，但仍用「目前看起來」。
- `0.50 - 0.69`：輸出混合型，例如「I 偏 S」，並追問確認。
- `< 0.50`：不要下結論，繼續問一題。
- 前兩名差距 `< 0.12`：視為混合型，不能硬判單一型。

#### 6. 階段判斷 state machine

後台以 phase 控制流程，不讓 LLM 自己決定是否推課。

```text
intake
  -> discovery
  -> profile_spec
  -> accuracy_check
  -> revise_profile 或 recommendation
  -> human_handoff 或 done
```

階段說明：

- `intake`：收基本資料，尚不聊天。
- `discovery`：一問一答找銷售天賦。
- `profile_spec`：產出銷售天賦規格。
- `accuracy_check`：固定問「你覺得有準嗎？像你嗎？」
- `revise_profile`：使用者說不像，追問並修正。
- `recommendation`：使用者認同後才推薦課程。
- `human_handoff`：需要真人接手。
- `done`：完成流程。

硬規則：

- `phase` 不是 `recommendation` 時，不能出現主推課程 CTA。
- `recognition.user_agreed !== true` 時，不能推薦課程順序。
- 使用者問價格 / 時間，但資料未確認時，不能回答具體數字或日期。
- 使用者說不像時，必須進入 `revise_profile`。

#### 7. 下一題選擇器

後台要決定下一題問什麼，不要讓 LLM 隨機聊。

優先順序：

1. 缺必要資料：生日、角色、地區、問題複選。
2. DISC 信心不足：問行為反應題。
3. 銷售天賦不明：問自然優勢題。
4. 卡點不明：問成交卡住的位置。
5. 情緒阻力明顯：先接情緒，再問一題。
6. 已可判斷：產出銷售天賦規格。

追問範例：

- 「當客戶說『我再想想』，你通常第一個反應是想追問、想解釋、想退一步，還是會先觀察他的表情？」
- 「你回想一下，過去成交比較順的客戶，是因為你很會開發、很會建立信任、很會說明價值，還是很會追蹤？」
- 「你比較怕客戶覺得你太強勢，還是比較怕自己講得不夠專業？」

#### 8. RAG 檢索規則

後台依 phase 決定可用資料，不同階段拿不同知識：

| phase | 可檢索資料 | 不可做 |
|---|---|---|
| intake | 生涯運數計算規則、基本題庫 | 不推課 |
| discovery | DISC、4U 問題樹、銷售天賦題庫 | 不推課 |
| profile_spec | 生涯運數、DISC、銷售天賦、4U 卡點 | 不放報名主 CTA |
| accuracy_check | 準確度確認話術 | 不推課 |
| revise_profile | 反向追問題庫、DISC 修正題 | 不推課 |
| recommendation | 五大課程 catalog、課程頁、course_offerings | 可推課 |

檢索 query 應包含：

```json
}
```

#### 10. 後處理安全檢查

LLM 回答產生後，後端再檢查：

- 是否在未認同前推課。
- 是否出現未確認日期、價格、名額。
- 是否出現未確認成效數字。
- 是否把生涯運數說成命定。
- 是否出現「保證成交」、「一定成功」等保證語。
- 是否包含非白名單連結。

若違規，後端重寫或回傳 fallback。

#### 11. 真人接手條件

以下狀況轉真人或 LINE：

- 使用者直接問最新日期 / 價格，但 `course_offerings` 無資料。
- 使用者是企業 / 團隊安排者，需要報價或客製訓練。
- 使用者連續兩次說診斷不像。
- 使用者有高意圖：「我想報名」、「我要買」、「可以匯款嗎」。
- 使用者提出客訴、退費、法律、醫療或高度敏感問題。
- 系統信心低於 0.50 且已追問三輪。

### 對話流程

1. 基本資料
   - 姓名或稱呼。
   - 西元生日。
   - 地區。
   - 身分角色。
   - 產業。
   - 想解決的問題，多選。
   - 目前目標，多選或單選。

2. 系統先做初判，但不先推課
   - 用生日計算生涯運數。
   - 用基本問題判斷初始卡點。
   - 用基本題目產生 DISC 初判，但信心不足時要在聊天中追問。
   - 此階段只用於決定追問方向，不直接顯示課程推薦。

3. 銷售天賦追問
   - 先接住情緒。
   - 再問一題最關鍵追問。
   - 追問重點不是「你要上哪堂課」，而是：
     - 你面對客戶時最自然的優勢是什麼？
     - 你成交卡住時最常出現的反應是什麼？
     - 你更擅長開場、建立信任、說服、追蹤，還是整理系統？
     - 客戶拒絕你時，你通常會衝、會退、會解釋，還是會先觀察？
     - 你比較需要被看見、被信任、被肯定，還是需要邏輯清楚？
   - 使用者回答後更新：
     - DISC 可能性。
     - 主要問題排序。
     - 最終目的。
     - 銷售天賦假設。
     - 銷售卡點假設。
   - 遇到「太貴、再想想、沒時間、以前上課沒效果、要問主管」等語句，後端取用 4U 異議處理，但移除未確認數字。

4. 先產出銷售天賦規格
   - 一段泰欣老師口吻總結。
   - DISC 初判與依據。
   - 生涯運數與銷售提醒。
   - 銷售策略。
   - 優點與天賦。
   - 容易卡住的地方。
   - 最適合的成交位置，例如：
     - 開發型。
     - 信任建立型。
     - 關係經營型。
     - 邏輯說服型。
     - 系統追蹤型。
     - 舞台表達型。
   - 結尾固定問：「你覺得有準嗎？像你嗎？」

5. 等使用者認同後再推薦課程
   - 若使用者回答「準、像、有中、滿符合」，才進入課程推薦。
   - 推薦語氣：
     - 「那如果這個方向是準的，我會建議你不要一次什麼都學，而是照一個順序補。這樣你會進步得更快。」
   - 再輸出：
     - 第一堂課推薦。
     - 第二 / 第三堂課路徑。
     - 為什麼這個順序適合他。
     - 課程頁、報名表單、LINE CTA。
   - 若使用者回答「不像、不準」，AI 要先追問修正，不推課。

```text
我先幫你整理一下，我目前看到的是：

1. 你的銷售天賦
```

### 課程時間與金額規劃

使用者要求頁面要明確可見開課時間與金額，因此需要新增單一權威資料源。建議優先方案：

1. Google Sheet 作為後台資料表。
   - 欄位：course_id、course_name、region、date_time、price、early_bird_price、venue、status、signup_url、updated_at、verified_by。
   - 後端 `/api/course-offerings` 只讀這份資料。

2. 若尚未提供最新資料。
   - 官網顯示「待泰欣團隊確認」或「請洽 LINE 取得最新場次」。

### LLM 安全規則

- 不編造日期、價格、名額、成效。
- 未在 course_offerings 找到資料時，不能自行推測。
- 未確認案例數字只能轉成不帶數字的概念敘述。
- 不做醫療、心理診斷式斷言。
- 生涯運數是學習與溝通參考，不是命定結論。
- 前半段優先引導學生認識自己，不先推課。
- 課程推薦只能在使用者認同診斷後自然銜接。
- 如果使用者不認同診斷，要先修正判斷，不進入課程銷售。

### 後台 SOP

#### SOP 1：知識庫建置

目的：把泰欣老師資料整理成後端可檢索、可控管、可追溯的資料。

流程：

1. 來源盤點
   - 4U 內部站。
   - 生涯運數計算器。
   - 五大課程頁。
   - TaixinMemoryHub 課程 catalog。
   - 未來新增的課程講義、逐字稿、案例、QA。

2. 切塊
   - 每段只放一個主題。
   - 不把多個課程、案例、異議混在同一段。
   - 每段保留 source_path 與 source_title。

3. 標籤
   - `source`
   - `module`
   - `course`
   - `disc`
   - `audience`
   - `problem`
   - `phase_allowed`
   - `safety_level`

4. 安全分級
   - `public_safe`：可直接對外說。
   - `internal_guidance`：只能作為推理，不直接照抄。
   - `needs_verification`：含日期、價格、名額、成效數字，未確認不可對外。
   - `private_only`：不進公開 AI。

5. 測試
   - 隨機抽 20 筆 chunk，確認來源、標籤、使用階段正確。
   - 對含數字的 chunk 做安全標記檢查。

#### SOP 2：課程時間與金額維護

目的：讓官網與 AI 都只回答已確認的最新課程資訊。

流程：

1. 建立 `course_offerings` 權威資料源。
2. 欄位固定：
   - course_id
   - course_name
   - region
   - date_time
   - price
   - early_bird_price
   - venue
   - status
   - signup_url
   - updated_at
   - verified_by
3. 每次開課資訊更新後，先由人工確認。
4. 後端只讀這份資料，不讀 LLM 記憶。
5. 前端顯示「最後更新日期」。
6. 若資料空白，顯示「待確認」或導 LINE，不顯示假日期 / 假價格。

#### SOP 3：學生對話流程

目的：確保每個學生都先被理解，再被推薦。

流程：

1. Intake
   - 收基本資料。
   - 告知生日用途：用於生涯運數與銷售天賦分析。
   - 不預設儲存完整生日。

2. Discovery
   - 問 2 到 5 題。
   - 每題只問一件事。
   - 優先問行為反應，不問抽象性格。

3. Profile Spec
   - 產出銷售天賦規格。
   - 不推課。
   - 固定問：「你覺得有準嗎？像你嗎？」

4. Accuracy Gate
   - 使用者認同：進入 recommendation。
   - 使用者不認同：進入 revise_profile。
   - 使用者沒回答：追問感受，不推課。

5. Recommendation
   - 只在認同後推薦。
   - 推薦第一堂、第二堂、第三堂。
   - 說明順序原因。
   - 顯示課程頁 / 報名 / LINE。

6. Handoff
   - 高意圖、企業需求、價格日期不明、低信心、敏感問題，導真人。

#### SOP 4：後端回應產生

目的：避免 LLM 自由發揮造成亂推課或亂報資訊。

流程：

1. 後端組 prompt 前，先準備 structured context。
2. 只放本輪 phase 允許使用的 knowledge chunks。
3. system prompt 固定禁止：
   - 未認同前推課。
   - 猜日期 / 價格。
   - 使用未確認成效數字。
   - 保證結果。
4. 要求 LLM 回 JSON。
5. 後端做 schema validation。
6. 後端做安全後處理。
7. 前端只渲染後端批准的欄位。

#### SOP 5：端到端測試

每次上架前至少測：

1. 台灣銷售顧問，生日有效，問題：成交不了 + 看不懂客戶。
   - 預期：先產出銷售天賦規格，不先推課。

2. 馬來西亞主管，問題：團隊不會成交 + 表達複製。
   - 預期：先分析主管型銷售天賦，認同後才推課。

3. 使用者回答「不像」。
   - 預期：AI 追問修正，不推課。

4. 使用者回答「很準，像我」。
   - 預期：AI 才推薦課程順序與 CTA。

5. 使用者問「最近什麼時候開課」但 course_offerings 無資料。
   - 預期：不回答日期，導 LINE 或表單。

6. 使用者問「多少錢」但 course_offerings 無資料。
   - 預期：不回答價格，導 LINE 或表單。

7. 使用者要求保證成效。
   - 預期：不保證，只說可協助找出學習路徑。

8. mobile / desktop 檢查。
   - 預期：表單、聊天、銷售天賦規格、認同按鈕、CTA 不重疊。

#### SOP 6：營運檢查

每週或每次活動前檢查：

- course_offerings 是否最新。
- 報名表單是否可用。
- LINE 連結是否可用。
- 最新課程頁是否仍存在。
- AI 是否仍遵守認同閘門。
- 是否有學生常問但 AI 答不好的問題，需要補知識庫。

## 2026-07-07 實作補充：DISC 討厭題與課程資料源

### 基本題新增邏輯

使用者補充：一開始可以問「銷售上最討厭做哪些事」與「職場上最討厭哪一種人」，用討厭項目反推 DISC。MVP 已改成三題四選一：

1. 銷售上你最討厭做哪一件事？
2. 職場上你最受不了哪一種人？
3. 客戶互動中，最讓你卡住的是？

判斷原則：

| 選項訊號 | 對應 DISC | 背後意義 |
| --- | --- | --- |
| 討厭拖延、沒結果、沒有下一步 | D | 想要效率、推進、結果 |
| 討厭冷冰冰、沒互動、被忽略 | I | 想要共鳴、互動、被看見 |
| 討厭被壓迫、衝突、硬逼決定 | S | 想要安全感、穩定、關係不被破壞 |
| 討厭沒邏輯、資料混亂、承諾沒根據 | C | 想要依據、結構、可驗證 |

三題各自送入 `disc_hate_sales`、`disc_hate_workplace`、`disc_hate_customer`，每題對應 DISC 加權 2.2 分。後續聊天內容仍會繼續修正分數，不把基本題當成絕對定論。
